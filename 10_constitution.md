# Конституция проекта LLM Budget Manager

Жёсткие ограничения для архитекторов, разработки, DevOps и QA. Решение, которое нарушает любой принцип, недопустимо без изменения конституции (раздел «Управление»).
Источники: `06_ceo_verdict.md` §5 и §8, `02_legal.md`, `02_certification.md`, ответы заказчика `10_tech_qa.md`.

## Основные принципы

### I. Только метаданные, никогда содержимое
Утилита не принимает, не хранит и не журналирует текст запросов и ответов моделей. Хранится только состав из FR-034: субъект, подразделение, модель, токены, стоимость, время, статус, решение. В журналах сотрудник фигурирует под псевдонимом, сопоставление доступно только администратору. Детальные события хранятся 12 месяцев, после этого удаляются. Источник: красная линия 1 юриста, 152-ФЗ, ст. 86–88 ТК РФ.

### II. Утилита не вызывает модели и не распоряжается токенами
Утилита только принимает решения и ведёт учёт. Она не проксирует вызовы, не хранит ключи провайдеров для вызова моделей, не перепродаёт токены (BYOK — красная линия 2). **Единственное исключение** — ключи администратора Anthropic и OpenAI для импорта расхода. Они передаются только через переменные окружения или хранилище секретов и никогда не попадают в репозиторий, журналы, ответы API, UI и резервные копии в открытом виде.

### III. Утилита не останавливает работу AI (fail-open по умолчанию)
Недоступность, медленный ответ или ошибка утилиты либо импорта не должны останавливать вызовы моделей. По умолчанию действует fail-open с таймаутом 50 мс на стороне вызывающей системы. Fail-closed допускается только как явная настройка отдельной политики. Отказной тест (SC-002) — обязательный гейт каждого релиза. Сбой импорта никогда не влияет на выдачу решений.

### IV. Без интернета, кроме одного исключения за флагом
Утилита полностью работает без исходящего интернета: без телеметрии, внешних CDN, загрузки шрифтов и проверок обновлений. **Исключение:** исходящие обращения разрешены только к API расхода провайдеров (Anthropic, OpenAI) для импорта расхода. Они идут за флагом конфигурации, который по умолчанию выключен и может быть выключен в любой момент. При выключенном флаге исходящих соединений наружу нет ни одного, и это проверяется тестом. Внешний канал уведомлений допускается только во внутреннюю сеть заказчика.

### V. Чистые лицензии и цепочка прав
В поставке только open source из белого списка разрешительных лицензий (MIT, Apache-2.0, BSD-2/3, ISC, PostgreSQL License и аналогичные — согласовывается с юристом). Запрещены: каталог `enterprise/` LiteLLM и любой код с отдельной коммерческой лицензией; GPL, AGPL и SSPL в поставке и модифицированные копилефт-компоненты; иностранное проприетарное ПО с обязательной онлайн-активацией. SCA и SBOM обязательны в CI на каждом релизе (SDL платформы, ГОСТ Р 56939). Исключительные права на код принадлежат заказчику: код подрядчиков принимается только с отчуждением прав. Источник: красная линия 3, `02_certification.md`.

### VI. Деньги считаются точно, один раз и прослеживаемо
Каждое списание прослеживается до своего основания: события Decision API, строки импорта или подписки. Один и тот же расход не может попасть в бюджет из двух источников: у каждого источника провайдера ровно один способ учёта. Обработка отчётов и импорта идемпотентна. Суммы хранятся в ₽ с исходной валютой и курсом. Округление и ошибки с плавающей точкой не допускаются (SC-007 — совпадение до копейки). Решения allow/deny/redirect детерминированы и объяснимы: в ответе есть применённый лимит, причина и дата сброса. Вероятностная логика в критическом пути решения не допускается.

### VII. Сначала тест, потом код; готово — значит проверено
Приёмочные тесты сценариев P1 и пограничных случаев пишутся до реализации и сначала падают. Работа считается выполненной только с приложенным выводом тестов: `verification-before-completion`. Пороги SC-001…SC-011 проверяются автоматическими тестами: нагрузочным, отказным, тестом идемпотентности, матрицей ролей, проверкой отсутствия содержимого.

### VIII. Простота и рамки бюджета
v1 — это одна установка docker compose на одном сервере, без компонентов «на вырост». Все функции доступны через API, админка — клиент этого API, MCP повторяет операции API с той же семантикой. Рамки: ≤ 2 млн ₽ и ≤ 4 чел.-мес. до Г2. Прогноз превышения означает остановку и решение заказчика. Расширение объёма возможно только через техлида. Порядок урезания: MCP и IdP → внешний канал уведомлений → коннектор OpenAI.

### IX. Русский язык и понятные отказы
Интерфейс, сообщения об отказе, уведомления и документация администратора — на русском. Код, идентификаторы и машиночитаемые коды ошибок (`budget_exceeded`, `model_not_allowed` и т.д.) — на английском, единые для HTTP API и MCP. Все даты и границы периодов — по МСК.

## Дополнительные ограничения

- **Среда v1:** локально, Docker (docker compose), один сервер или ноутбук. Kubernetes, российские ОС и реестр — следующий этап, но решения v1 не должны их исключать: без привязки к иностранным облакам и без компонентов, недоступных on-prem.
- **Конфигурация и секреты:** только через переменные окружения и `.env.example`. Секретов в репозитории нет.
- **Доступ:** у каждой вызывающей системы свой отзываемый ключ. В админке ролевая модель с минимальными правами. Все изменения настроек пишутся в журнал аудита.
- **Право:** до включения режима «ограничивать» на реальных сотрудниках у заказчика должны быть локальный акт о мониторинге использования ИИ и ознакомление работников.

## Процесс и гейты качества

- Контракт API (`12_openapi.yaml`) — источник истины. Изменения вносит главный архитектор через техлида.
- Перед релизом: зелёные приёмочные, нагрузочные (SC-001) и отказные (SC-002) тесты, SCA без критических уязвимостей и запрещённых лицензий, SBOM приложен.
- Разработка не начинается без явного согласия заказчика на архитектуру (`12_approval_log.md`).
- Работы сверх прототипа и спайка финансируются только после прохождения Г1 (`06_ceo_verdict.md` §8; критерий Г1 уточняется — `10_tech_spec.md`, отклонение D3).

## Управление

Конституция имеет приоритет над остальными документами техкоманды. Изменение принципа возможно только с письменным решением заказчика и записью в `10_tech_qa.md`: что меняется, почему, последствия. Каждое ревью и PR проверяется на соответствие принципам I–IX. Сложность сверх необходимой должна быть обоснована в ADR.
