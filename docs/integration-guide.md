# Руководство по интеграции с LLM Budget Manager

**Для кого:** разработчики шлюзов, агентов и сервисов, которые вызывают LLM от имени сотрудников или
служебных субъектов. **Версия API:** контракт `12_openapi.yaml` 1.0.2. **Задача:** T091.

Коротко: перед каждым вызовом модели спросите решение (`POST /api/v1/decisions`), вызовите ту модель, которую
вернула утилита, и сообщите фактический расход (`POST /api/v1/usage`). Если утилита не ответила за 50 мс,
действуйте по `fail_mode`: при `open` выполните вызов и положите отчёт в буфер, при `closed` откажите с кодом
`policy_unavailable`. Всё это уже делает эталонный клиент `budget_client` (раздел 5).

## 1. Подключение

| Что | Где взять |
|---|---|
| Адрес утилиты | `http://<BIND_ADDR>:<API_PORT>` установки, по умолчанию `http://127.0.0.1:8080` (руководство администратора) |
| Ключ вызывающей системы | Админка → «Вызывающие системы» → «Создать». Ключ показывается **один раз**; храните его как секрет |
| Заголовок | `X-Api-Key: <ключ>` в каждом запросе |
| Формат | JSON, UTF-8; время — ISO 8601 со смещением (утилита отвечает в МСК, `+03:00`); деньги — строка с двумя знаками (`"30.00"`, ₽) |

**Область субъектов ключа (`subject_scope`)** задаётся при создании ключа и потом не меняется:

| `subject_scope.type` | Кого можно указывать в `subject` |
|---|---|
| `service` | только `{"type": "service"}`; расход идёт на подразделение ключа (`department_id`) |
| `department_employees` | сотрудников одного подразделения (`department_id`) |
| `any_employee` | любого сотрудника из загруженной оргструктуры |

Субъект вне области → `403 subject_out_of_scope`, попытка пишется в журнал аудита. Так агент, которого
уговорили сослаться на чужого сотрудника, не потратит чужой бюджет.

Сотрудник указывается учётной записью AD: `{"type": "employee", "login": "ivanov"}`. Логин утилита сразу
заменяет псевдонимом (`emp-…`); в журналах и отчётах логинов нет.

**Содержимое запросов к моделям утилите не передаётся никогда.** Схемы запросов закрыты
(`additionalProperties: false`): лишнее поле, например `prompt`, даёт `422 validation_error`.

## 2. Протокол: решение → вызов модели → отчёт

```
вызывающая система                 LLM Budget Manager               провайдер LLM
        │  POST /api/v1/decisions  ──►  (таймаут 50 мс)
        │  ◄── 200 {outcome, model, decision_id, reserve_rub, http_status_hint, …}
        │  outcome = deny → вернуть пользователю отказ (http_status_hint + message), модель НЕ вызывать
        │  outcome = allow | redirect → вызвать модель `model` ───────────────────────────►
        │  ◄─────────────────────────────────────────────────────────── usage (токены)
        │  POST /api/v1/usage {report_id, decision_id, tokens, call_status} ──►
        │  ◄── 200 {status: charged | duplicate, amount_rub, flags, expense_date}
```

### 2.1. Запрос решения — `POST /api/v1/decisions`

```json
{
  "subject": {"type": "employee", "login": "ivanov"},
  "model": "claude-sonnet-4-5",
  "kind": "chat",
  "input_tokens": 1200,
  "max_output_tokens": 800,
  "needs": {"tools": true, "json_mode": false, "context_tokens": 0}
}
```

- `model` — идентификатор модели из каталога утилиты (админка → «Модели»).
- `input_tokens` / `max_output_tokens` — оценка. Если их нет, берутся значения по умолчанию из каталога
  (`estimate.source = catalog_default`), и резерв может оказаться неточным.
- `needs` — возможности, без которых запрос не выполнится. При перенаправлении утилита выбирает только модели,
  которые их поддерживают.
- `kind = embedding` — модели эмбеддингов никогда не перенаправляются.

### 2.2. Ответ — всегда `200`, даже при отказе

Отказ по бюджету или модели — это **решение, а не ошибка** (ADR-005): статус `200`, `outcome = deny`.

| `outcome` | Что делать |
|---|---|
| `allow` | вызвать `model` (совпадает с запрошенной) |
| `redirect` | вызвать **`model`** из ответа — более дешёвую модель, которая помещается в остаток (`reason = budget_exceeded`). Пользователю можно показать `message` |
| `deny` | модель не вызывать; вернуть пользователю отказ со статусом `http_status_hint` и текстом `message` |

Поля, полезные шлюзу:

| Поле | Значение |
|---|---|
| `decision_id` | передаётся в отчёт о расходе |
| `reserve_rub`, `expires_at` | сумма резерва по оценке и срок его жизни (`RESERVATION_TTL_MIN`, по умолчанию 15 мин). Пока отчёта нет, резерв уменьшает остаток |
| `http_status_hint` | подсказка, какой HTTP-статус вернуть своему клиенту: `200` (allow/redirect), `403` (`model_not_allowed`), `429` (`budget_exceeded`), `422` (`model_unknown`, `subject_unknown`) |
| `code` | только при `deny`: `model_not_allowed`, `budget_exceeded`, `model_unknown`, `subject_unknown` |
| `applied_limit` | самый строгий из лимитов, который определил решение, и дата его сброса по МСК (`resets_at`) |
| `policy_mode` | `observe` / `warn` / `enforce` — режим политики подразделения |
| `observed_violation` | в режимах `observe` и `warn` нарушение не блокирует вызов (`outcome = allow`), но указывается здесь. В режиме `warn` покажите пользователю `message` |
| `fail_mode` | `open` / `closed` — как поступать, если утилита недоступна (раздел 3) |
| `budget_blocked_by_subscriptions` | `true` — остаток съели подписки (амортизация мест), а не вызовы |
| `message` | объяснение на русском, его можно показывать пользователю как есть |

**Коды отказа `deny`:**

| `code` | Когда | `http_status_hint` |
|---|---|---|
| `model_not_allowed` | модель не разрешена подразделению субъекта | 403 |
| `budget_exceeded` | оценка не помещается в остаток, и подходящей более дешёвой модели нет | 429 |
| `model_unknown` | модели нет в каталоге или она выключена | 422 |
| `subject_unknown` | сотрудника нет в оргструктуре или он не состоит ни в одном подразделении | 422 |

**`subject_unknown` у ключа без подразделения** (14_tech_rulings.md, В1-2). Для неизвестного субъекта
подразделения нет, поэтому в ответе: `policy_mode = enforce`, `fail_mode` = `DEFAULT_FAIL_MODE` установки
(по умолчанию `open`), `department_id = null`. Исход — отказ в любом режиме политики.

### 2.3. Отчёт о расходе — `POST /api/v1/usage`

```json
{
  "report_id": "0b0e6c1e-6a52-4f0e-9a9e-3c1f5a7d2b10",
  "decision_id": "6f1c…",
  "tokens": {"input": 1180, "output": 640, "cached": 0},
  "call_status": "ok"
}
```

- `report_id` (UUID) генерирует **вызывающая система** до отправки. Вместе с ключом он образует ключ
  идемпотентности: повтор с тем же `report_id` или тем же `decision_id` вернёт `status = duplicate`, а сумма
  не изменится. Поэтому при любом сомнении (таймаут, обрыв соединения) отчёт можно просто повторить.
- Отчёт присылается и при `call_status = aborted` или `error`: провайдер мог взять деньги за входные токены.
- Цена — по каталогу на момент решения, в рублях по курсу месяца даты расхода.
- Ответ `200` приходит только после записи в БД.
- Если вызвали не ту модель, которую вернула утилита, укажите её в `actual_model`: расход спишется по
  фактической модели с флагом `decision_not_followed`.
- Отчёт не пришёл до истечения резерва — резерв списывается по оценке с флагом `no_report`. Поздний отчёт
  заменит оценку фактом.

**Отчёт без решения** (вызов выполнен при fail-open, раздел 3): без `decision_id`, но с `subject`, `model` и
`occurred_at` — временем вызова, а не досылки. Расход относится к дате `occurred_at` по МСК.
Ограничения: `occurred_at` не старше 7 суток и не дальше 5 минут в будущем.

**Пакетная досылка — `POST /api/v1/usage/batch`:** до 1 000 отчётов (больше → `413 batch_too_large`).
Строки обрабатываются независимо, в ответе на каждую `{index, ok, result | error}`.

### 2.4. Ошибки запросов

Ошибки возвращаются как `application/problem+json`: машинный `code` и `detail` на русском.

| Статус и `code` | Операция | Причина | Что делать |
|---|---|---|---|
| `401 unauthorized` | все | нет ключа, ключ неверный или отозван | ошибка конфигурации: не маскировать fail-open |
| `403 subject_out_of_scope` | `decisions`, `usage`, `balance` | субъект вне области ключа | ошибка интеграции или попытка злоупотребления |
| `404 decision_not_found` | `usage` | `decision_id` не найден или принадлежит другому ключу | проверить, что отчёт уходит с тем же ключом |
| `422 validation_error` | все | лишнее или неверное поле | исправить запрос |
| `422 subject_unknown` | `usage` без решения | сотрудника нет в оргструктуре | отчёт останется в буфере как отклонённый; передать администратору |
| `422 model_unknown` | `usage` без решения или с `actual_model` | модели нет в каталоге | то же |
| `422 fx_rate_missing` | `usage`, `decisions` | нет курса валюты модели за месяц расхода | администратор вводит курс месяца; отчёт дослать повторно |
| `404 subject_unknown` | `balance` | сотрудник не найден, или ключ не `service`, а `login` не передан | передать `login` известного сотрудника |
| `413 batch_too_large` | `usage/batch` | больше 1 000 строк | делить пакет |

`422` у отчёта без решения (`subject_unknown`, `model_unknown`, `fx_rate_missing`) — это не сбой утилиты.
Повтор того же отчёта без исправления данных вернёт ту же ошибку.

### 2.5. Остаток — `GET /api/v1/balance`

`GET /api/v1/balance?login=ivanov` возвращает остатки по всем применимым лимитам (личные и подразделения;
день, неделя, месяц). Для ключа `service` параметр `login` не передаётся, возвращаются лимиты подразделения
ключа. Пустой список `limits` означает, что лимиты не заданы.

В каждом лимите: `spent` (вызовы, импорт, подписки), `reserved_rub`, `remaining_rub` (может быть
отрицательным), `used_pct` (доля **расхода** от лимита, без резервов; может быть больше 100), `over_limit`
(расход больше лимита).

## 3. Эталонная схема: таймаут 50 мс, fail-open и буфер

Утилита не должна становиться точкой отказа для вызывающих систем (FR-006, SC-002). Схема:

1. **Таймаут 50 мс на весь запрос решения** (соединение + ответ). Утилиту ставят в той же сети, что и
   вызывающую систему.
2. **Сбой утилиты** — таймаут, нет соединения, `5xx`, `408`, `429`, испорченный ответ. Поведение зависит от
   `fail_mode` субъекта:
   - `open` (по умолчанию) — вызов модели **выполняется** без решения, отчёт о расходе пишется в локальный
     буфер без `decision_id`, с `subject`, `model` и `occurred_at`;
   - `closed` — вызов **отклоняется** вызывающей системой с кодом `policy_unavailable` (это код вызывающей
     стороны, в ответах утилиты его нет).
3. **Ошибки запроса** (`401`, `403`, `404`, `422`) — не сбой утилиты. Их нельзя скрывать под fail-open,
   иначе отозванный ключ или неверная интеграция останутся незамеченными.
4. **Откуда брать `fail_mode`, когда утилита не отвечает.** `GET /api/v1/integration-config` отдаёт
   `default_fail_mode` и `fail_mode` по подразделениям; обновлять раз в `refresh_s` (60 с) с `If-None-Match`
   (ответ `304`, если ничего не изменилось). Кэш храните на диске, чтобы он пережил перезапуск. Каждое решение
   тоже содержит `fail_mode` субъекта — запомните его по субъекту.
5. **Буфер отчётов** — на диске, запись надёжная, до возврата управления (у `budget_client` это SQLite с
   `synchronous=FULL`). Ключ строки — `report_id`, поэтому повторная досылка не создаёт дублей.
6. **Досылка** — пакетами через `usage/batch` (у `budget_client` по 500), при сбое пауза 0,5 → 1 → 2 … ≤ 30 с.
   Принятые строки из буфера удаляются. Строки, отклонённые с `4xx`, больше не досылаются и остаются в буфере
   для разбора (`rejected()`).
   Досылайте не позже чем через 7 суток: более старые отчёты без решения не принимаются.

## 4. Рекомендация: закрыть прямой доступ к провайдерам

Утилита учитывает только те вызовы, о которых ей сообщили. Чтобы бюджет нельзя было обойти:

- выпускайте ключи провайдеров (Anthropic, OpenAI) только для шлюзов, которые интегрированы с утилитой; у
  сотрудников и агентов собственных ключей быть не должно;
- закройте исходящий доступ к `api.anthropic.com` и `api.openai.com` со всех хостов, кроме этих шлюзов
  (межсетевой экран или корпоративный прокси);
- расход по ключам, проектам и рабочим пространствам вне шлюзов учитывайте импортом: админка → «Источники»,
  способ учёта `import`. Источники шлюзов отмечайте способом `decision_api` и привязывайте к ключу вызывающей
  системы — тогда импорт по ним только сверяется с отчётами и не списывается второй раз.

## 5. Эталонный клиент `budget_client` (Python)

Пакет `app/client/budget_client`: Python ≥ 3.11, только стандартная библиотека, без телеметрии. Сеть — только к
`base_url`, переменные `HTTP(S)_PROXY` не применяются.

```bash
pip install ./app/client/budget_client
```

```python
from pathlib import Path
from uuid import uuid4

from budget_client import BudgetClient, ClientRequestError, PolicyUnavailable

client = BudgetClient("http://bm.local:8080", api_key, Path("/var/lib/my-gateway/budget"))  # timeout_ms=50
subject = {"type": "employee", "login": "ivanov"}


def handle(request):
    try:
        d = client.decide(subject, "claude-sonnet-4-5", "chat", input_tokens=1200, max_output_tokens=800)
    except PolicyUnavailable:
        return error_response(503, code="policy_unavailable")  # fail-closed: утилита недоступна
    except ClientRequestError as e:  # 401/403/404/422 — ошибка интеграции, не сбой утилиты
        log.error("budget: %s %s", e.status, e.code)
        raise
    if d.outcome == "deny":
        return error_response(d.http_status_hint, code=d.code, message=d.message)

    report_id = str(uuid4())  # до вызова модели: повтор отчёта не создаст дубля
    usage, status = call_model(d.model, request)  # d.model — с учётом перенаправления
    client.report(
        decision_id=d.decision_id,  # None при fail-open
        tokens={"input": usage.input_tokens, "output": usage.output_tokens},
        call_status=status,  # ok | aborted | error
        report_id=report_id,
        subject=subject,
        model=d.model,
    )
    return response(...)
```

| Поведение | Значение |
|---|---|
| `decide()` | ждёт не дольше `timeout_ms` (50 мс). При сбое: `fail_mode = open` → `outcome="allow"`, `fail_open=True`, `decision_id=None`; `closed` → `PolicyUnavailable` |
| `report()` | пишет отчёт в буфер на диске и будит фоновую досылку. Без `decision_id` нужны `subject` и `model`; `occurred_at` подставляется временем вызова |
| Фоновый поток | раз в 60 с обновляет `integration-config`, досылает буфер |
| `flush()` | досылка вручную, например перед остановкой процесса |
| `pending()` / `rejected()` | сколько отчётов ждут досылки и какие окончательно отклонены сервером |
| `close()` / `with BudgetClient(...)` | останавливает фоновый поток |

### Каталог состояния `state_dir`: права и ПДн

В `state_dir` клиент хранит два файла на каждый ключ (имя содержит отпечаток ключа):

- `config-<отпечаток>.json` — кэш `integration-config` и `fail_mode` по субъектам;
- `buffer-<отпечаток>.sqlite3` — буфер отчётов.

**Ключа API в этих файлах нет**: на диск пишется только его отпечаток (первые 12 знаков SHA-256). Но в буфере
и кэше лежат **логины субъектов (учётные записи AD) — это персональные данные**, а также модели и число
токенов. Содержимого запросов к моделям в них нет. Поэтому:

- каталог должен принадлежать пользователю процесса вызывающей системы, права `0700` (файлы `0600`);
  другим пользователям хоста и резервным копиям общего назначения он недоступен;
- не размещайте его на общих и сетевых томах;
- принятые сервером отчёты из буфера удаляются, а окончательно отклонённые (`rejected()`) остаются для
  разбора. Разбирайте их и удаляйте по регламенту хранения ПДн.

## 6. Что не входит в v1

- **MCP не поставляется.** В контракте описан интерфейс MCP (`/mcp`, раздел `x-mcp-tools`: `request_decision`,
  `report_usage`, `get_balance`), но в версии 1 он урезан решением контрольной точки недели 5
  (`14_checkpoint_week5.md`). Интеграция — только через HTTP API из этого руководства. Агенты, которые
  умеют только MCP, подключаются через свой шлюз, а шлюз ходит в HTTP API.
- Клиент есть только для Python. Для других языков реализуйте схему из раздела 3 сами: она занимает
  три HTTP-запроса и локальную очередь.

## 7. Проверка интеграции

1. Создайте ключ вызывающей системы и тестового сотрудника с маленьким дневным лимитом.
2. Запросите решение и отправьте отчёт. В админке «Журнал событий» появится вызов со списанной суммой.
3. Превысьте лимит: решение `redirect` или `deny budget_exceeded`, у шлюза — `http_status_hint = 429`.
4. Остановите утилиту: при `fail_mode = open` вызовы идут, `client.pending()` растёт. Запустите утилиту —
   `pending()` вернётся к 0, в журнале событий нет дублей.
5. Поставьте подразделению `fail_mode = closed` и повторите шаг 4: вызовы отклоняются с `policy_unavailable`.
