# 10. Задание архитекторам: LLM Budget Manager v1

**Кому:** архитектор AI (`11_arch_ai.md`), архитектор classic (`11_arch_classic.md`) — работаете независимо, не читаете чужое предложение. Судья — главный архитектор.
**От:** техлид, 2026-10-13. **Входы:** `10_tech_spec.md` (главный), `10_constitution.md` (жёсткие ограничения), `10_tech_qa.md`; по необходимости — `02_po.md` (Decision API, fail-open, критерии), `02_legal.md`, `02_certification.md`, `06_ceo_verdict.md` §5, §8.

## Что спроектировать

Внутреннюю утилиту бюджетов и лимитов на LLM. Сама она модели не вызывает.
1. **Decision API** «разрешить / отказать / перенаправить на самую дешёвую совместимую», с резервом суммы и отчётом о расходе после вызова: FR-001…FR-011, сценарии 1–2.
2. **Модель бюджетов**: подразделения (группы AD из файла), сотрудники, лимиты в ₽ на день, неделю и месяц по МСК, каталог моделей с ценами и возможностями: FR-012…FR-016.
3. **Подписки** с ручным вводом и равномерной амортизацией по дням, курс USD/₽ на месяц: FR-017…FR-020.
4. **Импорт расхода** Anthropic и OpenAI раз в сутки, справочник источников, дедупликация с Decision API: FR-021…FR-025.
5. **Единое правило остатка** (FR-026) — центральный модуль, который используют решения, админка, отчёты и уведомления.
6. **Админка на русском**, роли, CSV, уведомления 80/100%, аудит: FR-027…FR-032. **MCP-инструменты**: FR-033.
7. **Эталонная схема интеграции вызывающей стороны** (таймаут 50 мс, fail-open, буфер отчётов с досылкой) — для отказного теста SC-002.
8. **Поставка**: docker compose на одной машине, резервное копирование и восстановление (FR-037).

## Ключевые вопросы, на которые предложение обязано ответить

- Как получить p95 ≤ 10 мс на решение при 50 rps (SC-001) и не терять подтверждённые отчёты при перезапуске (SC-003)?
- Как резервы и параллельные решения держат перерасход ≤ 2% (SC-004)? Какую гарантию вы даёте и как её проверить?
- Как устроен расчёт остатка по FR-026 (факт + резервы + импорт по загруженным суткам + амортизация по дням) и как обеспечено совпадение до копейки (SC-007)?
- Как импорт обрабатывает задержку до суток, уточнения провайдера (замена, а не добавление), поздние данные за закрытый период и ровно один способ учёта на источник?
- Как выбирается «самая дешёвая совместимая» модель: детерминированно, с учётом всех лимитов, без перенаправления эмбеддингов?
- Как хранятся и передаются ключи администратора провайдеров (принцип II) и как флаг гарантирует ноль исходящих соединений (принцип IV)?
- Как MCP и HTTP API разделяют одну семантику и одни коды без дублирования логики?
- **Только архитектор AI:** где ML или LLM реально даёт выигрыш по этой спецификации. Принцип VI запрещает вероятностную логику в критическом пути решения. Если выигрыша нет, напишите это прямо. Допустимые кандидаты — вне критического пути и за флагом. Например, оценка токенов до вызова при отсутствии оценки от вызывающей стороны; подсказки по совместимости моделей. Для каждого нужен фолбэк без ML.
- **Только архитектор classic:** покажите самое простое решение, которое закрывает P1 и P2 в рамках бюджета.

## Ограничения (кратко; полный список — конституция)

- Только метаданные, псевдонимы, хранение 12 месяцев. Утилита не проксирует вызовы. Fail-open по умолчанию.
- Без интернета, кроме API расхода Anthropic и OpenAI за выключаемым флагом.
- Лицензии из белого списка. Нет `enterprise/` LiteLLM, GPL, AGPL, SSPL. SCA и SBOM обязательны.
- Docker на одной машине. Решения не должны закрывать путь к on-prem, Kubernetes и российским ОС на следующем этапе.
- **Бюджет: ≤ 2 млн ₽ и ≤ 4 чел.-мес. до Г2** при ставке 0,48 млн ₽/чел.-мес. (`06_ceo_verdict.md` §2). Это и есть рамка: 2,0 / 0,48 ≈ 4,2 чел.-мес. [Вывод]. Оценку дайте по ролям в чел.-неделях. Обязательно покажите, что войдёт при урезании объёма в порядке из принципа VIII, если полный объём не помещается.
- Эталонный стенд для SC-001 (CPU, RAM, диск) выберите и зафиксируйте сами, с обоснованием. Цифр производительности без источника или замера не приводить.

## Как главный архитектор будет выбирать

Стоп-факторы: нарушение любого принципа конституции; невыполнение сценариев P1 (1–3); оценка выше 4 чел.-мес. без плана урезания, который сохраняет P1; хранение содержимого запросов или ключей в открытом виде; исходящие соединения при выключенном флаге.
