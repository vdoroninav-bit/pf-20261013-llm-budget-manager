## В1. Плашка отставания импорта для владельца бюджета

**Вопрос.** FR-027 требует показывать на панели отставание импорта, но `getImportStatus` недоступна для `budget_owner`.

**Решение.** Добавить `budget_owner` в `x-roles` операции `getImportStatus`. Для этой роли сервер отдаёт сокращённый ответ: `unallocated_sources = []`, `last_error_class = null`. Остальные поля отдаются как есть: `enabled`, `configured`, `last_success_day`, `last_run_at`, `lag_hours`, `consecutive_failures`. На панели владелец видит плашку с теми же текстами, что А и Ф (`screens.md` §2), но:
- ссылки на экран 7 нет;
- при `consecutive_failures ≥ 2` вместо «Подробности — в разделе «Импорт провайдеров»» пишется «Администратор получил уведомление»;
- пункта меню «Импорт провайдеров» у владельца по-прежнему нет.

**Основание.**
- FR-027 — обязательное требование («админка ДОЛЖНА показывать по подразделению … отставание импорта»). Панель владельца — основной экран сценария 6.1. Без правки FR-027 для владельца закрыт лишь частично.
- FR-030: владелец видит «своё подразделение, только чтение расхода». В статусе импорта нет данных других подразделений: это общее состояние утилиты, и оно определяет полноту *его* остатка (FR-026, импорт за «загруженные сутки»).
- Список `unallocated_sources` — идентификаторы workspace и проектов провайдера, с которыми работает только администратор (справочник `provider-sources` — `x-roles: [admin]`). Класс ошибки нужен для разбора сбоя, а это тоже задача администратора. Поэтому оба поля для владельца скрываются: принцип минимизации, как `subject_pseudonym = null` у финансиста.

## В2. Расход по личному лимиту сотрудника в админке

**Вопрос.** Нужна ли операция «остаток сотрудника» (`getEmployeeBalance`) для карточки сотрудника?

**Решение.** Нет, в v1 операция не добавляется. Карточка сотрудника (экран 3.5) показывает только значения личных лимитов. Под ними подсказка:
> «Остаток по личному лимиту в админке не показывается. Отказы по нему видны в журнале событий: решение «Отказ», код «Бюджет исчерпан», сотрудник — по псевдониму.»

Кнопку перехода в журнал не делаем: у `listEvents` нет фильтра по псевдониму, а добавлять его — это расширение контракта.

**Основание.**
- FR-027 и сценарий 6.1 требуют показывать в админке остатки **по подразделению**. Остаток по личному лимиту в UI не требуется ни одним FR и ни одним сценарием приёмки.
- FR-026 (вычисление остатка по каждому лимиту) уже выполняется: остаток считается в `Budget.balance()`, участвует в решениях (FR-003) и доступен вызывающим системам через `getCallerBalance`.
- T043 описывает экран так: «сотрудники по псевдонимам с личными лимитами», то есть только лимиты. Принцип VIII: новая операция — это новый роутер, правила доступа и тесты вне рамки 4 чел.-мес.
- Кандидат в бэклог v1.1: «`getEmployeeBalance` для А и В (своё подразделение)».

**Что меняется.**
| Файл | Изменение | Кто |
|---|---|---|
| `12_openapi.yaml` | — | — |
| `design/screens.md` §3.5 | добавить подсказку выше; вопрос В2 закрыть ссылкой на этот файл | дизайнер |

## В3. Признак «бюджет занят подписками» на панели

**Вопрос.** В `LimitBalance` нет булева признака. Можно ли считать его как `subscriptions_share_pct ≥ 100.0`?

**Решение.** Нет. Признак считается так:
```
blocked = spent.subscriptions_rub > 0  И  spent.subscriptions_rub ≥ limit_rub
```
Обе величины — `Money`. Сравниваются как целые копейки после разбора строки, без `float` (принцип VI). `subscriptions_share_pct` используется только для текста «Подписки занимают N% бюджета периода» и для сравнения с `Department.subs_warn_pct`. Строку процента тоже разбирать без `float`: целая и дробная часть отдельно или десятичный тип.

**Основание.**
- `12_arch_decision.md` §4.5 п. 8 задаёт признак нормативно: «`budget_blocked_by_subscriptions=true`, если амортизация за период ≥ лимита». Это сравнение сумм, а не процентов.
- `subscriptions_share_pct` округлён до 0,1 (`pattern ^[0-9]+\.[0-9]{1}$`) и необязателен. При доле 99,95–99,99% он покажет `100.0`, хотя платные вызовы ещё проходят. Расхождение панели с решением API нарушило бы SC-007 по смыслу («остаток в админке совпадает с API»).
- Условие `> 0` нужно для лимита `0.00`, который допускается `LimitSet`. Без подписок пометка «занят подписками» при нулевом лимите была бы ложной.

**Что меняется.**
| Файл | Изменение | Кто |
|---|---|---|
| `12_openapi.yaml` | — (поле не добавляем: признак однозначно выводится из уже отдаваемых сумм) | — |
| `design/screens.md` §2, строка «Доля подписок» | заменить «если ≥ 100» на правило выше | дизайнер |
| `src/pages/Dashboard.tsx` (T072) | вычисление признака по правилу выше; юнит-тест на 99,99% (`share_pct = 100.0`, признака нет) и на лимит `0.00` без подписок | frontend |
| **Пометка для backend** (T021, тест T012) | привести `Decision.budget_blocked_by_subscriptions` к тому же правилу: `amort > 0 и amort ≥ limit` для применённого лимита. Это уточнение п. 8 §4.5 для нулевого лимита, контракт не меняется | backend 1 |

## В5. Значения `error_class` импорта и код отказа по выключенной модели

**Вопрос 1.** Какие классы ошибок возвращает импорт?

**Решение.** Закрытый перечень `ImportErrorClass` (новая схема в контракте) используется в `ImportStatus.providers[].last_error_class` и `ImportRun.error_class`:

| Значение | Когда | Текст в UI (`13_design.md` §7.4) |
|---|---|---|
| `auth_rejected` | провайдер ответил 401/403 на ключ администратора | «Провайдер отклонил ключ администратора. Проверьте ключ на сервере.» |
| `provider_unavailable` | сеть, таймаут, 429 или 5xx провайдера | «Провайдер не ответил. Загрузка повторится по расписанию.» |
| `bad_response` | ответ не разобран: изменился формат | «Провайдер вернул данные в неожиданном формате. Нужна проверка коннектора.» |
| `internal` | прочая ошибка утилиты при обработке | «Загрузка не удалась из-за внутренней ошибки. Подробности — в журнале контейнера worker.» |

Для неизвестного значения (если сервер новее клиента) frontend показывает «Загрузка не удалась» и класс моноширинным, как предложил дизайнер.

**Основание.** Сценарий 5.5 и FR-025 различают «провайдер недоступен» и «ключ отклонён». Риск R-4 в `10_tech_spec.md` добавляет смену формата. Четыре класса покрывают эти случаи и остаток. Открытая строка в контракте сделала бы тексты UI недоказуемыми тестом (принцип VII). Таблица `job_run.error_class` (`12_plan.md`) внутренняя и в API не выходит, перечень на неё не распространяется.

**Вопрос 2.** Какой код получает решение по выключенной модели (`active=false`)?

**Решение.** `deny model_unknown`. Выключенная модель также не входит в кандидаты перенаправления. Открытые резервы по ней закрываются по отчёту или по сроку. Текст диалога выключения модели (экран 4):
> «Выключить модель {id}? Новые запросы к ней получат отказ «Модели нет в каталоге». На неё больше не будут перенаправляться запросы. Уже выданные резервы закроются по отчёту или по истечении срока. История цен и расход сохранятся.»

**Основание.** `12_arch_decision.md` §4.5 п. 2: «Модели нет в каталоге или она неактивна — `deny model_unknown`». П. 7: кандидат должен быть «активна». Пограничный случай «Модель удалена из каталога» в `10_tech_spec.md`.

## В6. Ограничения файла AD и защита последнего администратора

**Вопрос 1.** Максимальный размер и число строк файла AD.

**Решение.** Размер — не больше **10 МиБ** (10 485 760 байт). Если больше — `413 file_too_large`, ничего не применяется. Отдельного лимита строк нет. Порог — константа в коде, без переменной окружения. Проверка на клиенте до отправки: «Файл больше 10 МБ. Выгрузка групп AD обычно гораздо меньше — проверьте, что выбран нужный файл.» Тот же текст при `413` с сервера.

**Основание.** Защита от исчерпания памяти: `import_ad_csv(data: bytes, …)` читает файл целиком (T041). [Гипотеза] 10 МиБ — порог с большим запасом. Строка `login;display_name;group;is_primary` занимает порядка 50–100 байт, то есть 10 МиБ — это более 100 тыс. строк. Это заведомо больше оргструктуры пилота, поэтому лимит строк не нужен. Принцип VIII: одна константа, без настройки.

**Вопрос 2.** Защита от отключения последнего администратора.

**Решение.** `updateAdminUser` отвечает `409 last_admin` и ничего не меняет, если после изменения не останется ни одного пользователя с `role=admin` и `active=true`. Это касается смены роли с `admin` на другую и `active=false`. Отключить себя можно, если есть другой активный администратор. В UI (экран 10) переключатель «Отключить вход» и смена роли у единственного активного администратора выключены с подсказкой «Это единственный активный администратор. Сначала назначьте другого.» Текст для `409`: «Нельзя оставить систему без активного администратора.»

**Основание.** Без защиты администратор одной операцией лишает систему управления. В контракте нет пути восстановления через API, а `ADMIN_INITIAL_*` (T016) описан только как создание первого администратора. FR-030 требует, чтобы роль «Администратор (всё)» существовала. Проверка — один запрос в той же транзакции, что и `config.apply`.

## В7. Таймауты и частота обновления в админке

**Вопрос.** NFR для админки нет. Дизайнер предлагает 10 с до сообщения «Загрузка дольше обычного», обновление панели и колокольчика раз в 60 с, запусков импорта — раз в 10 с.

**Решение.** Значения приняты как **константы интерфейса, а не NFR**. Они не проверяются как критерии успеха, пометка [Гипотеза] в `screens.md` снимается с формулировкой «решение техлида, значения UI». Константы держать в одном модуле frontend. Правила:
- **10 с** — показ «Загрузка дольше обычного…» и кнопки «Повторить». Запрос при этом не обрывается.
- **60 с** — автообновление панели и счётчика колокольчика только при видимой вкладке (`document.visibilityState === 'visible'`).
- **10 с** — обновление «Запусков» только пока есть строки `queued` или `running`. Затем опрос останавливается.
- **Порог отставания импорта — один, по SC-008**, и на панели, и на экране 7: если сейчас позже 12:00 МСК, а `last_success_day` раньше вчерашних суток UTC, показывается `warning`. Отдельный порог «> 36 ч» на экране 7 убрать, `lag_hours` показывать числом без своего порога.

**Основание.**
- Нагрузка от опроса несущественна по сравнению с SC-001 (50 rps на Decision API) [Вывод: даже десятки открытых вкладок дают доли rps].
- 60 с совпадает с `refresh_s` (`IntegrationConfig`) и с минутным циклом фоновых задач (T071: пороги раз в минуту), поэтому чаще обновлять бессмысленно.
- Единый порог по SC-008 убирает выдуманное число и не даёт двум экранам показывать разное.

**Что меняется.**
| Файл | Изменение | Кто |
|---|---|---|
| `12_openapi.yaml` | — | — |
| `screens.md` §2 «Состояния», §7.1 «Отставание», §7.3, §11 | снять [Гипотеза], заменить порог «> 36 ч» правилом SC-008 | дизайнер |
| frontend (T002/T072/T064) | модуль констант UI; тест «опрос запусков останавливается без `queued`/`running`» | frontend |
