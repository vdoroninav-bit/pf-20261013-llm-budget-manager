# 14. Решения техлида по вопросам разработки

**Дата:** 2026-10-14
**Вход:** разделы «Вопросы техлиду» в `14_dev_backend.md` (Phase 2: T015–T019) и `14_dev_frontend.md` (T002).
**Основания:** `10_constitution.md` (принципы IV, VII, VIII, «Процесс»), `10_tech_spec.md`, `12_arch_decision.md`, ADR-006.
**Объём:** не расширяется. Добавлены одна переменная окружения (`SESSION_COOKIE_SECURE`) и настройка сбора метрик, без которой T086 не измеряет то, что заявлено. Остальное — уточнение существующих задач.
**Контракт:** `12_openapi.yaml` 1.0.1 → **1.0.2**. Меняются только объявления ответов 401/403 (Б1). Правку внёс техлид как решение главного архитектора (конституция, «Процесс»: изменения контракта идут через техлида).

## Сводная таблица

| № | Вопрос | Решение | Кому делать | Где |
|---|---|---|---|---|
| Б1 | Сервер отдаёт 401/403 там, где контракт их не объявляет (`logout`, `changePassword`, `listNotifications`, `markNotificationRead`) | **Принято, контракт 1.0.2.** У всех 50 операций с `security: session` объявлены `401 Unauthorized` и `403 Forbidden`. Исключение — `me`: у неё только 401 (CSRF нет, доступна всем ролям и до смены пароля). В описании `Forbidden` перечислены причины: роль или чужое подразделение (`forbidden`, пишется в аудит), CSRF (`forbidden`), не сменён временный пароль (`password_change_required`). Код `password_change_required` добавлен в примеры `Problem.code`. Схемы, пути и прочие статусы не менялись | Техлид — правка контракта (сделано). Backend — отказные ответы в тестах T016/T019 проверять через `assert_matches_contract`. Frontend — `npm run gen:api` и версия `1.0.2` в `resources.contract.test.ts` | Контракт — сделано. Backend — T042 (пункт «Доводка»). Frontend — первый шаг T043 |
| Б2 | Флаг `Secure` у cookie `bm_session` | **Добавить переменную `SESSION_COOKIE_SECURE`** (bool, по умолчанию `false`). По умолчанию API слушает `127.0.0.1` по HTTP, и с `Secure` браузер не вернул бы cookie. При HTTPS на обратном прокси заказчик ставит `true`. Конфигурация только через окружение — так требует конституция | Backend: `bm/settings.py`, установка cookie, тест на оба значения. DevOps: `deploy/.env.example` и `docs/admin-guide.md` | Backend — T042. DevOps — T087, T090 |
| Б3 | Нужна ли переменная окружения для срока сессии (12 ч) | **Нет.** Константа `SESSION_TTL = 12 ч` остаётся (принцип VIII: без настроек «на вырост»). Значение описывается в руководстве администратора. Если заказчик попросит другое — меняется константа | DevOps — описать в руководстве | T090 |
| Б4 | Прокси для коннекторов: `trust_env=False` не пускает импорт через корпоративный прокси | **Сейчас не делаем, `trust_env=False` остаётся.** Неявный прокси из окружения нарушал бы проверяемость принципа IV: трафик уходил бы туда, куда указывает окружение, а не код `egress`. Нужен ли прокси, зависит от контура заказчика, а это неизвестно. **Вопрос заказчику** (до начала T062): «Можно ли из сервера утилиты выйти на `api.anthropic.com` / `api.openai.com` напрямую или только через корпоративный прокси?» Если только через прокси — расширение объёма оформляется отдельно: явная переменная `IMPORT_HTTPS_PROXY` (по умолчанию пусто), применяется только для `anthropic`/`openai` и только при `IMPORT_ENABLED=true`, к webhook не применяется; тест «флаг выключен → 0 соединений, включая прокси» | Техлид — задать вопрос заказчику. Backend — ничего до ответа | T062 (пометка в задаче) |
| Б5 | `period_start` для уведомлений без периода (NULLS NOT DISTINCT) | **`period_start` не бывает NULL.** `create_once` отклоняет `None` (`ValueError`). Правила ключа: `import_failure`, `import_unallocated` — `department_id=NULL`, `period=NULL`, `period_start` = дата МСК обнаружения (не больше одного уведомления каждого вида в сутки); `fx_missing` — `period_start` = 1-е число месяца без курса (одно на месяц); `reservation_no_report` — подразделение резерва и дата МСК обнаружения. Пороговые и `subs_share` — без изменений. Даты по МСК — принцип IX. Ограничение: при сбое обоих провайдеров в одни сутки создаётся одно `import_failure`. В его тексте перечисляются провайдеры, которые сбоили на момент создания, подробности по каждому — на экране «Состояние импорта» (`getImportStatus`). Схему и ключ уникальности не меняем | Backend | Проверка `None` и ключи импорта — T061. `fx_missing` и `reservation_no_report` — T071 |
| Б6 | Метрики при `UVICORN_WORKERS=2` считаются по процессам отдельно | **Multiprocess-режим prometheus-client.** Каталог задаётся через `PROMETHEUS_MULTIPROC_DIR`, режим агрегации у gauge указывается явно. Без этого `/metrics` отдаёт данные случайного воркера, и p95 из гистограммы в T086 недостоверен. Это не расширение: T086 уже требует брать p95/p99 из `/metrics` | Backend — `bm/metrics.py` и тест. DevOps — переменная и `tmpfs` у `api`, очистка при старте | Backend — T031. DevOps — T087 |
| Б7 | (Известное ограничение) Повторный резолв хоста webhook (DNS rebinding) не контролируется | **Принять как ограничение v1.** Webhook разрешён только на частные адреса. В руководстве рекомендуется указывать IP | DevOps — руководство | T090 (внесено в формулировку) |
| Ф1 | Критерий T002 «`grep -rE "https?://" dist` пуст» недостижим | **Принят новый критерий:** `npm --prefix app/frontend run test && npm --prefix app/frontend run build` дают exit 0. Шаг `build` включает `scripts/check-dist.mjs`, проверку по белому списку: в `index.html` и CSS — никаких адресов, в JS — только namespace, `http://localhost` как база `new URL()`, адреса в текстах ошибок и адрес телеметрии ra-core. Мутационная проверка (подложенный CDN-адрес даёт exit 1) показана в отчёте. Принцип IV требует отсутствия **загрузок и исходящих обращений**, а не строк в бандле. Строки в текстах ошибок ничего не загружают | Frontend — ничего дополнительно. Техлид — формулировка T002 исправлена, задача отмечена `[x]` по выводу из `14_dev_frontend.md` (101/101 тест, `build` и `check-dist` дают exit 0) | T002 — закрыта |
| Ф2 | Телеметрия react-admin: оставить отключённой флагом с тестом или вырезать при сборке | **Оставить `disableTelemetry` и тест.** Плагин Vite, переписывающий код ra-core, хрупок при обновлениях и сам становится непроверяемым кодом. Тест с мутационной проверкой ловит снятие флага. Условие: адрес телеметрии остаётся в белом списке `check-dist` только вместе с этим тестом. Удалили тест — удаляется и разрешение. Тест «0 исходящих» QA (T089) на стенде дополнительно подтверждает, что браузер админки ничего не загружает с внешних адресов | Frontend — ничего дополнительно (условие уже выполнено) | T002 — закрыта |

## Последствия для текущего состояния

- **Фронтенд-тест станет красным до первого шага T043.** `src/__tests__/resources.contract.test.ts` проверяет, что `info.version == '1.0.1'`. После перехода на 1.0.2 он падает — так и задумано: это сигнал перегенерировать `schema.d.ts`. Действие frontend: `npm run gen:api`, затем заменить ожидаемую версию на `1.0.2`. Задача на ~15 минут [Гипотеза], сделать первым коммитом frontend. T002 закрыта по выводу, полученному на контракте 1.0.1. Поведение сборки правка контракта не меняет: добавлены только ответы.
- **Backend:** правка контракта только расширяет множество объявленных статусов. Тесты `tests/contract/*` проверяют необъявленный статус на `healthz` (418), поэтому их правка не ломает [Вывод, по коду `test_helper_rejects_undeclared_status`]. Нужен прогон `make test` после правки: проверку (а) «спецификация валидна» должен подтвердить backend или QA, у техлида нет Bash.
- **Открытый вопрос заказчику:** Б4 (прокси). На текущие задачи не влияет. Ответ нужен до начала T062.
- **Отклонения backend 1–5** из `14_dev_backend.md` (сигнатура `get_client`, запрет `urllib`/`http` целиком, per-file-ignores в тестах, код `password_change_required`, `422 invalid_credentials` в `changePassword`) приняты без изменений. Отклонение 4 закреплено в контракте (Б1).
